# AGENTS.md: ReplenishPlusPlus

## What this is

A **server-side Paper plugin** (plugin name `ReplenishPlusPlus`, package `dev.replenishplusplus`) for **Minecraft 26.3** (`api-version: "26.3"`), Java **25**, built with **Maven** (no Gradle). Two features: **auto-replant for crops** modeled on Hypixel's Replenish (a player breaks a mature crop, the plugin replants it) and a **Teleport Pads** recreation of the Hypixel SkyBlock block (`/rpp pad`), plus an op-only **dev mode** (`/rpp dev`) as a testing utility, pads and dev mode are deliberately kept outside the harvest pipeline. Only runtime dependency is `paper-api` (provided scope, pinned to `26.3.build.35-alpha`, see gotchas for why there is no version range); `me.lucko:spark-api` `0.1-SNAPSHOT` (provided, resolved from `repo.lucko.me`) is declared for a future spark integration but no code imports it yet; test-only deps are JUnit via a BOM (see Build & run). License: **AGPL-3.0**. Repo: `github.com/Mitra-88/ReplenishPlusPlus`.

**HARD REQUIREMENT, vanilla-faithful, opt-in, dupe-proof, lag-safe.** The plugin only acts for players who opted in (`/rpp toggle`, default on) and otherwise behaves exactly like vanilla, sneak bypass, wrong tool, missing seed, disabled crop, or global-off all fall through to a normal break. For supported crops, mature drop counts come from `VanillaCropDrops`' hardcoded tables transcribed exactly from the vanilla loot table JSONs staged in `loot_tables/` (MC 26.3, transcription-of-record, maintainer-approved performance amendment, see Loot table sync), with fortune read straight off the tool via `getEnchantmentLevel`; anything the tables do not cover falls back to vanilla `block.getDrops()` (Fortune applies); nothing is invented. A consumed seed is **always refunded** (dropped at the block, or at the player when its chunk is unloaded) when a queued replant fails, the two deliberate exceptions are queue-full backpressure (refunding there would spawn thousands of item entities in exactly the lag scenario the caps exist for) and a player who quit before an unload-abandoned replant (the chunk is unloaded, so every refund location would force-load chunks, the same thing the caps prevent). The HIGHEST/MONITOR two-phase listener split is the dupe protection: a break that gets canceled after the decide phase, or whose drop suppression another plugin undoes (`isDropItems` back to true at commit), pays out nothing. The lag-protection caps (per-tick limit, queue limit, drop instead of throw) are load-bearing. Any change that invents drops, dupes seeds, pays out canceled breaks, or weakens the caps violates the design contract, push back on requests that would require it.

## Coding rules (mandatory: apply to every change)

**Purpose:** implement only what is genuinely necessary for the requested feature.

**Core rules**

- No overengineering.
- No unnecessary abstractions.
- No generic framework-like constructs when a simple, direct solution suffices.
- No "future-proofing" without a concrete need.
- No dead helper classes, wrappers, managers, registry layers, or utility collections without a clear current use case.
- No artificially bloated architectures.

**Style guidelines**

- Write simple, direct, readable code.
- Prefer concrete implementations over unnecessary generalization.
- Keep classes small and single-purpose.
- Keep methods short and clear.
- Use self-explanatory names instead of comments. **Java sources carry no comments at all**, every rationale, invariant, and quirk lives in this file instead, so it has exactly one home and can't drift from the code. Don't re-add inline comments or Javadoc; put the knowledge here.
- Never use em dashes. In any file (docs, config comments, chat messages, code strings) write the sentence with commas, colons, or plain hyphens instead.


**What to avoid**

- AI-typical "enterprise" patterns for small features.
- Excessive use of interfaces without real added value.
- Builders, factories, services, providers, adapters, etc., unless actually needed.
- Defensive abstractions for hypothetical future use cases.
- Multi-layered architecture for trivial logic.
- Duplicated helper logic in "Utils" just to make code look "cleaner".
- Complex configuration or event systems for simple flows.

**Implementation principle, for every change:**

1. What is the specific requirement?
2. What is the smallest clean solution?
3. Implement exactly that, nothing beyond it.

**Minecraft plugin specifics**

- Use the Paper API directly whenever possible.
- Do not add an abstraction layer just to "decouple" the API without a valid reason.
- Keep listeners, commands, and config handling only as complex as necessary.
- Server-side only: all game logic runs on the main thread, and the performance-critical `ReplantQueue` stays flat and allocation-conscious, don't "clean it up" into object graphs or wrappers.
- No artificial splitting of small features across numerous files.

**Refactoring** happens only for a real benefit: better readability, less duplication, clearer responsibilities, or a necessary technical fix, never purely stylistic preference.

**When in doubt, prefer:** less code, fewer files, less abstraction, less magic.

**Goal:** the code should feel pragmatically and deliberately written by an experienced plugin developer, not like generic AI output.

## Ponytail, lazy senior dev mode

Adapted from [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail/blob/main/AGENTS.md), commit `b6c04480c03e8db2f035751d7c46289779ec3362`.

You are a lazy senior developer. Lazy means efficient, not careless. The best code is the code never written.

Before writing any code, stop at the first rung that holds:

1. Does this need to be built at all? (YAGNI)
2. Does it already exist in this codebase? Reuse the helper, util, or pattern that's already here, don't re-write it.
3. Does the standard library already do this? Use it.
4. Does a native platform feature cover it? Use it.
5. Does an already-installed dependency solve it? Use it.
6. Can this be one line? Make it one line.
7. Only then: write the minimum code that works.

The ladder runs after you understand the problem, not instead of it: read the task and the code it touches, trace the real flow end to end, then climb.

Bug fix = root cause, not symptom: a report names a symptom. Grep every caller of the function you touch and fix the shared function once, one guard there is a smaller diff than one per caller, and patching only the path the ticket names leaves a sibling caller still broken.

Rules:

- No abstractions that weren't explicitly requested.
- No new dependency if it can be avoided.
- No boilerplate nobody asked for.
- Deletion over addition. Boring over clever. Fewest files possible.
- Shortest working diff wins, but only once you understand the problem. The smallest change in the wrong place isn't lazy, it's a second bug.
- Question complex requests: "Do you actually need X, or does Y cover it?"
- Pick the edge-case-correct option when two stdlib approaches are the same size, lazy means less code, not the flimsier algorithm.
- Mark deliberate simplifications that cut a real corner with a known ceiling (global lock, O(n²) scan, naive heuristic) with a `ponytail:` note naming the ceiling and upgrade path; in this repo that note lives here in AGENTS.md (next to the relevant section or in Gotchas & quirks), never as an inline Java comment.

Not lazy about: understanding the problem (read it fully and trace the real flow before picking a rung, a small diff you don't understand is just laziness dressed up as efficiency), input validation at trust boundaries, error handling that prevents data loss, security, accessibility, the calibration real hardware needs (the platform is never the spec ideal, a clock drifts, a sensor reads off), anything explicitly requested. Lazy code without its check is unfinished: non-trivial logic leaves ONE runnable check behind, the smallest thing that fails if the logic breaks (an assert-based demo/self-check or one small test file; no frameworks, no fixtures). Trivial one-liners need no test.

(Yes, this also applies to agents working on this repo. Especially to them.)

## How a harvest works

1. `ReplenishPlusPlusListener` is two-phase over `BlockBreakEvent`: the **HIGHEST** handler (`ignoreCancelled = true`) decides, it bails out for non-survival game modes, suppressed drops (`!event.isDropItems()`, i.e. another drop plugin owns the break), unknown crops (checked first after the event sanity checks, one `EnumMap` lookup rejects every non-crop break before any player-data or config access), global-off, disabled crops, player-toggle-off, sneaking (if `sneakToBypass`), wrong tool, missing anchor, or a non-`Ageable` block, then suppresses vanilla drops and stashes a `HarvestPlan`. The **MONITOR** handler commits, consumes the seed, enqueues the replant, distributes drops, only for a break that was not canceled *and* is still ours (`isDropItems()` false at commit; a plugin that re-enabled drops after our suppression owns the break), so a late-canceled break pays out nothing (that's the dupe protection; keep the split). The decide handler is try/catch-wrapped, keep that.
2. Mature: drops computed via the transcribed tables (`matureDrops` → `VanillaCropDrops` with the tool's fortune level; vanilla's crop tables read fortune and nothing else) with `block.getDrops(tool, player)` kept as the fail-safe; if `requirePlayerSeed`, the decide phase peeks `SeedIndex.hasSeed` (abort with a "need seed" message if absent) and the commit phase consumes through `SeedIndex.consume` (if the seed vanished between the phases, the consume fails, drops are still paid, the need-seed message plays, and the replant is skipped); `event.setDropItems(false)`, vanilla drop logic is fully bypassed; drops go straight to the inventory (`DropPickupManager.giveOrDrop`, gated by `directPickup`) or drop naturally at the block center. Immature: replanted at the same age, no seed, no drops, never table-fed. Dev-mode exception: when the breaker has `/rpp dev` on (and `dev.full-age-replant` is enabled), every crop they break replants at max age, mature and immature alike, so crops replanted fresh before dev was enabled normalize to full age, while the seed contract is untouched (immature still gives no drops and consumes no seed); the age is decided at enqueue, the `HarvestPlan` carries a `mature` flag that feeds the dev harvest counter.
3. The replant is **scheduled, not immediate**: `plugin.enqueueReplant(...)` → `ReplantQueue` (a timing wheel); a random 1..N ticks later (N = `replantDelayTicks`, default 3) the main-thread tick task replants with precomputed `BlockData` from `AgeMetaRegistry`. The randomization is deliberate: a fixed delay would make every break from N consecutive ticks come due in one tick (burst load that scales with N), while spreading replants evenly keeps the per-tick cost flat at roughly breaks-per-tick no matter how large N is. Failures play the `replant-failed` sound and refund the seed.
4. Seed-cache invalidation: any inventory click invalidates `SeedIndex`, and so do drags, hand swaps, and item pickups/drops when a seed material is involved, plus right-clicking a block while holding a seed (50 ms per-player cooldown); player notifications use per-type cooldowns, wrong-tool warnings share a 2 s per-player cooldown and the need-seed warning has its own 5 s cooldown, so the two never suppress each other.

Cocoa is special-cased everywhere (`instanceof CocoaCropInfo`): anchor = adjacent jungle log, facing packed into the queue entry, resolved original-facing → player-facing → any adjacent jungle. Nether wart anchors to soul sand; all other crops to farmland.

## Codebase tour

All code under `src/main/java/dev/replenishplusplus/`, flat two-level packages:

**Root**, `ReplenishPlusPlus` (`JavaPlugin` main). Owns the `AtomicReference<ConfigCache>`, `AgeMetaRegistry`, `ReplantQueue`, `PlayerToggleManager`, `DevModeManager`, `TeleportPadManager`, `UpdateChecker`. `reloadLocalConfig()` is the single reload path: reloads the language file into `Messages` (`YamlConfiguration.loadConfiguration` on `plugins/ReplenishPlusPlus/en_us.yml`, absent/broken keys keep the built-in defaults), builds a fresh `ConfigCache` via `ConfigCache.from(getConfig(), issues)`, logs every issue as a `[Config]` warning, swaps the cache in If `reloadLocalConfig` bails early (failed `reloadConfig()`, or a `config.yml` that parses to no settings, e.g. invalid YAML, whose parse error `YamlConfiguration` swallows, keeps the previous settings and returns early with an issue), `onEnable` creates the queue from the active cache immediately afterwards, so `replantQueue` can never stay null while the harvest pipeline is live; rebuilds the queue and flushes the old one, and returns the issue list (the `/rpp reload` output shows it to admins); `en_us.yml` itself is written out at enable via `saveResource("en_us.yml", false)`. `onDisable()` shuts dev mode down (cancels the clear task, any pending profiler auto-stop, and the counting state, and removes the water-speed modifier), saves `pads.yml`, and flushes the queue, `flush()` is the shutdown (cancels the task, drains every pending entry, then returns the count replanted).

**`listener/`**, `ReplenishPlusPlusListener`: the two-phase harvest flow (HIGHEST decide → MONITOR commit, see "How a harvest works"); mature drops come from `matureDrops` (`VanillaCropDrops` counts with the tool's fortune level read via `getEnchantmentLevel`, no enchantment map allocation, and `stacksFor` builds the ItemStacks; a null table falls back to `block.getDrops(tool, player)`); player warnings are throttled per message type, values in "How a harvest works" §4. `SeedCacheInvalidationListener`: every inventory-movement listener that invalidates `SeedIndex` (50 ms throttle, quit eviction), new inventory-mutation invalidations go here, not into the harvest listener.

**`queue/`**, performance-critical (recent perf work lives here); don't restructure casually.
- `ReplantQueue`, 8192-slot timing wheel (`1 << 13`) over a primitive-array pool (parallel `World[]/int[]/Material[]/UUID[]` arrays + free list, primed at 1024, grown up to `maxReplantsQueued`). Per-entry metadata is bit-packed into one int: age (8 bits) / cocoa facing (2) / retry count (8) / seed-consumed flag (1). All public methods `synchronized`; `flush()` is the shutdown path. Delays above 8191 ticks are truncated with a warning; unloaded chunks retry up to 20 times, then `refundSeedToOnlinePlayer` (seed dropped at the online player's feet + `replant-failed` sound; a quit player gets nothing, see gotchas); an enqueue arriving while the queue is not started refunds the same way immediately. Entries beyond `maxReplantsPerTick` in a single tick are deferred to the next wheel slot, only a queue-full enqueue drops. `replant(index)` is self-guarding, its own catch refunds the seed, callers never wrap it, and a shared 16-entry chunk-loaded memo (`isChunkLoadedCached`, per-entry tick-stamped) serves both `tick()` and `flush()`; entries are stamped with `Bukkit.getCurrentTick()` so a cached answer never leaks across ticks (a chunk that loads/unloads between ticks must be re-checked, or retry/abandon decisions act on stale state), and the sixteen slots keep multi-chunk farms from thrashing the memo every replant. Both replant writes (`replantNormal`/`replantCocoa`) call `setBlockData(data, false)`: `applyPhysics=false` skips only the changed block's neighbor physics while client sync still fires, so replants render without a relog, and the survival physics it skips is redundant because `CropInfo.lacksAnchorAt` validated the anchor immediately before the write.
- `QueueStats`, record for `/rpp debug queue`.

**`crop/`**, `CropType` enum is the single source of truth for supported crops (block material, seed, required tool, display name, plus the `fromMaterial`/`fromName` lookups; no crop behavior lives on it). Adding a crop = new enum constant + a `crops.<lowercase-name>` entry in `config.yml`/README (the key derives from the enum name, `ConfigCache.readCrops` reads it automatically, lenient on case and spaces) + a `VanillaCropDrops.counts` case, a listener `stacksFor` case, and `VanillaCropDropsTest` bounds/expectation cases, all three exhaustive switches so a missing one fails the build; if the vanilla table changed shape, re-run Loot table sync first. Everything else derives automatically. `AgeMetaRegistry` precomputes every age (cocoa: age × facing) `BlockData` at enable-time so replanting never mutates shared state. `CropInfo` is a sealed interface over `SimpleCropInfo` (farmland anchor, or soul sand for nether wart) and `CocoaCropInfo`, and it owns attachment logic: `plantsOn(Material)` + `validNeighborFaces()` are the single source of where a crop can grow, and the shared `lacksAnchorAt(world, x, y, z)` default walk is the only anchor check (negative form: both call sites bail out when it's true), the listener's decide phase and the queue's replant check both call it, so never duplicate that knowledge. `CocoaCropInfo` is the single cocoa authority: `FACES` + `face()`/`faceOrdinal()` (the packed facing order the queue's bit layout depends on, never re-create a parallel copy) plus the jungle-log anchoring. `HarvestTool` matches via vanilla item tags (`Tag.ITEMS_HOES` / `Tag.ITEMS_AXES`), resolved once per tool into a lazy `EnumSet` on first `matches` (lazy because the `Tag` constants need the live registry at call time, which is also why `HarvestTool` itself is deliberately untested offline).

**`config/`**
- `ConfigCache`, immutable record snapshot of all settings (incl. `checkUpdates`, which is consumed once at enable to build `UpdateChecker`, `/rpp reload` does not re-apply it; incl. the nested `DevOptions` record read from the `dev.*` keys, `fast-water`/`no-ice`/`inventory-clear`/`full-age-replant`/`harvest-counter`/`fast-growth`, all defaulting true, which gates the dev-mode features at runtime); swap via `AtomicReference`, never mutate (`withEnabled` for the global toggle). Crop toggles are an unmodifiable `Set<CropType>` of *disabled* crops (not in the set = enabled). `from(FileConfiguration, List<String> issues)` reads every scalar through `ConfigReader` (sound names via `stringValue`; player message strings are NOT here, they live in `en_us.yml`/`Messages`): absent keys fall back silently, but present-yet-invalid values (non-bool, non-number, section/list-typed, unknown message style / crop key / sound name, out-of-range volume/pitch, below-minimum caps, delay above the 10-tick maximum) are appended to `issues` and fall back too, never silently default a broken value. Note `reloadConfig()` layers the bundled `config.yml` in via `setDefaults`, so absent keys already read back bundled values at the read layer.
- `ConfigReader`, static permissive readers (`boolValue`/`intValue`/`floatValue`): they parse the string form of any scalar, fall back to the default when the key is absent, and report present-yet-invalid values into the issue list.
- `Messages`, the language layer: every player-visible chat message lives in `en_us.yml` (bundled resource, `saveResource`'d on enable, loaded by `reloadLocalConfig` so `/rpp reload` re-applies edits). Holds the shared `MINI_MESSAGE` instance, a `DEFAULTS` map of hardcoded English fallbacks, an `isString`-guarded overlay load (a broken/missing file silently keeps defaults), and the accessors: `prefixed(key, resolvers)` (prefix + key template, placeholders resolved), `prefixedRaw` (prefix + literal MiniMessage, for hardcoded one-offs), `bare`/`component` (no prefix), plus the `DOT` and gradient `LINE` constants for the admin screens.
- `MessageStyle`, CHAT / ACTION_BAR / NONE enum; `send(player, component)` is the single notification-routing point (used by the listener and `DropPickupManager`); `parse(String)` returns null for unknown values so the config layer can report and default.
- `SoundEffect`, record of (enabled, sound, volume, pitch) clamping volume 0–1 and pitch 0.5–2.0 (range constants are public for config validation); `play()` is the only sound path and no-ops when `enabled` is false.
- `SoundRegistryMapper`, lenient user sound names ("entity.item.pickup", "ENTITY_ITEM_PICKUP", …) → `Optional<Sound> lookup(String)` (empty on null/blank/unknown so callers can report the miss); separator/case-insensitive canonicalization via `Registry.SOUND_EVENT`; lazily loaded once. Every caller is main-thread today, the lazy init needs synchronization before any async use. `keyName(Sound)` renders a sound's registry key for display, the only supported key accessor (see gotchas).
- `PlayerToggleManager`, per-player toggle persisted in the player `PersistentDataContainer` (`replenishplusplus:enabled`) behind a lazy in-memory mirror (`Map<UUID, Boolean>`, populated on first `isDisabled`, updated by `toggle`, evicted on quit by the harvest listener), so the per-break check is a map lookup instead of a PDC read; the PDC stays the persisted source of truth and a relog resyncs the mirror.

**`util/`**, `VanillaCropDrops` (pure Java, no Bukkit types: `counts(CropType, int fortune, Random)` returns primitive counts, one slot per drop material in the order the listener's `stacksFor` maps them; constants transcribed from `loot_tables/`, see Loot table sync; the exhaustive switch over `CropType` is the missing-entry tripwire, a new constant cannot compile without a table case), `SeedIndex` (static per-player seed-slot cache: 36 storage slots, offhand = -2, none = -1; plain `HashMap`, all access is main-thread; `hasSeed` is the decide phase's peek, it never touches the inventory, it only (re)builds the cache; `tryConsume` decrements partial stacks by mutating the live item mirror directly instead of `Inventory#setItem`, so vanilla batches the client slot sync next tick instead of the API path forcing an immediate packet per consumed seed, the last-seed-in-slot path still uses `setItem(slot, null)`, which is required), `DropPickupManager` (`giveOrDrop(player, block, drops, ConfigCache)`: inventory-first, leftovers drop at the crop center, the center `Location` is computed lazily on first drop; leftovers trigger the `inventory-full` message + sound, a successful give plays `pickup`), `WarningThrottle` (3 s per-category log suppression with suppressed-count reporting; messages are `Supplier`s materialized only when actually logged, so suppressed warnings build no strings; the `Throwable` overload logs the stack trace on the first occurrence), `LocationUtil` (`describe`; centered drop points use Paper's `Location#toCenterLocation()`), `TextUtil` (enum-name prettifier).

**`update/`**, `UpdateChecker` (async GitHub releases check against the single `REPO` constant exposing `RELEASES_URL` plus the shared `downloadLink()`; the `update.available` key of `en_us.yml` is rendered by the join notice and `/rpp version`; the console log line carries its own hardcoded MiniMessage wording (a documented console exception); volatile state, failed checks complete as failed via `isCheckFailed()` instead of staying pending forever; strict structured tag parser: `[v]MAJOR.MINOR.PATCH[-alpha.N|-beta.N|-rcN][-mcMAJOR.MINOR-paper]`, precedence `release > rc > beta > alpha`, the `-mc` classifier is precedence-neutral, and anything else, including `+build` metadata, which exists only in artifact file names, fails the check; one-shot `onCheckCompleted` callbacks fired on the main thread on success only), `UpdateNotificationListener` (holders of `replenishplusplus.update`, default op, get a notice on join if the check already finished, otherwise the moment it completes).

**`dev/`**, `DevModeManager` + `DevModeListener`: the `/rpp dev` testing mode (permission `replenishplusplus.dev`, op). Deliberately invisible outside its own UX: no menu/help/status mention, no `dev:` section in the bundled `config.yml`, no line in the `/rpp reload` output, no README/permission-table row, `DEV_MODE.md` (unshipped, user-only) is its doc home; hand-added `dev.*` keys in `config.yml` still work (absent keys default true). Per-player, session-only (in-memory set, no PDC, relog turns it off, `onQuit` evicts). Every feature is gated by a `dev.*` config toggle (`ConfigCache.DevOptions`), with nobody in dev mode, the pipeline's entire dev cost is one boolean check per phase (decides `anyActive()`, commit's `isEmpty()` in `onHarvest`) and the tick task does not exist. Water: keyed transient `AttributeModifier` (+1.0 `WATER_MOVEMENT_EFFICIENCY`) applied on enable (skipped when `dev.fast-water` is off), removed on disable/shutdown, and re-applied on respawn via `PlayerRespawnEvent` (transient modifiers die with the respawned entity). Ice: `BlockFormEvent` cancelled for ICE/FROSTED_ICE while *any* player has dev on (world-level event, so this part is global; Frost Walker's `EntityBlockFormEvent` is a subclass and covered for free). The single tick task (period 20 = 1 s, scheduled only while a dev player is online) runs only the inventory clear; when `dev.inventory-clear` is off it returns after one config read. Growth: when `dev.fast-growth` is on, player-planted crops are set to max age inside `BlockPlaceEvent` (one `EnumSet` bit-test per placement, near-zero) and enabling dev mode sweeps the 25×25×5 volume around the player once, pre-filtered with allocation-free `World#getType` and setting every crop directly to max age, there is NO periodic growth work at all, because replants are already full-age (see full-age replant) and placed crops are instant; crops grown young by other means (e.g. farmer villagers) stay vanilla until dev is re-enabled or the crop is replanted. Inventory clear: every 20 ticks (when `dev.inventory-clear` is on), per player, an allocation-free 36-slot `getItem` scan early-exits once 4 free slots are found; otherwise the same scan keeps only hoes/axes (item tags) and a total budget of 64 units of the current crop's seed, the budget is per-total, not per-stack (first 64 seed units kept across stacks, excess seed stacks trimmed or deleted, and the harvest item itself is deleted too; before the first harvest, any crop's seed counts toward the budget), armor/offhand untouched; deleted amounts feed the `totalCleared` counter. ## Rules that matter for edits

- **Threading:** everything on the main thread except `UpdateChecker`'s HTTP call (its `console()` output reads `Messages` from the HTTP thread, which is why `Messages.load` builds a fresh overlay and publishes it through the `volatile messages` field, never mutate the published map in place) and `PadMenuListener.onChat`, which fires on the async chat thread and only touches the `ConcurrentHashMap pendingNames` before hopping back to the main thread via `runTask`. - **Config is immutable:** build a new `ConfigCache` and swap it in. New config keys must land in: `config.yml` (with its comment), `ConfigCache` (field + a `from()` read through `ConfigReader` with issue reporting), the README config section, and the `/rpp reload` output. Present-yet-invalid values must be reported via the issues list, never silently defaulted.

## Gotchas & quirks

- **Registry keys come from the registry, not the instance.** `Sound#key()`/`Sound#getKey()`, and the same pair on `Art`, `Dialog`, `PatternType`, `Structure`, `TrimMaterial`/`TrimPattern`, `MusicInstrument`, are `@Deprecated(forRemoval = true)` on all of these types, but the `since` varies (1.20.4 on `Structure` and the trim types, 1.20.5 on `Sound`/`PatternType`/`MusicInstrument`, 1.21 on `Art`, 1.21.8 on `Dialog`). Take keys via `Registry.SOUND_EVENT.getKey(sound)` (nullable, sounds can exist without a key) or `getKeyOrThrow`, and render them through `SoundRegistryMapper.keyName`. The generic `Keyed` accessors are not deprecated; only these per-type redeclarations are.
- **paper-api is pinned, not a range.** A range like `[26.3.build,)` silently resolved to the pre-release `26.3-pre-2.build.0-alpha` (Maven sorts `pre-2` above the `build.N` line), whose transitional API mismatches the final 26.3 docs. `Registry.SOUNDS` still exists on the final line as an obsolete, hidden alias of `SOUND_EVENT`; use `SOUND_EVENT`. Bump the pin by hand in `pom.xml`.
- `maxReplantsPerTick`/`maxReplantsQueued` clamp to ≥ 256 and `replantDelayTicks` clamps to 1..10 (`MAX_REPLANT_DELAY_TICKS`), out-of-range values are reported as config issues at load and clamped; the 1..N random replant window and its de-batching rationale are described in "How a harvest works" §3; the wheel's own `MAX_DELAY_TICKS` (8191) truncation stays as a queue-level guard but is unreachable from config.
- Queue-full (backpressure) and a quit player's unload-abandoned replant drop without refund by design, the only two such cases (rationale in "What this is"). Don't make them throw or grow unbounded.
- Mature harvests always replant at age 0 and consume a seed; immature harvests replant at the same age, never consume one, and suppress vanilla drops, restoring the crop while also paying its seed drop would let players mint seeds by re-breaking. The seed logic depends on that split.
- The two-phase listener is the dupe protection: a break that another plugin cancels after our HIGHEST handler (legal in Bukkit) must pay out nothing, breaks where another plugin already set `dropItems = false` are left alone entirely, and a plugin that re-enables `dropItems` after our decide-phase suppression also gets nothing from us (the commit handler checks `isDropItems()`). Never move seed consumption, drop payout, or replant scheduling back into the decide phase.
- `SeedIndex` caches slot numbers, any new inventory-mutation path must trigger `invalidateWithCooldown`, or the cache goes stale.
- **`getString` never returns null for a present section/list value.** `MemorySection.getString` does `val.toString()` on any non-null value, so a section-typed key reads back as garbage text like `MemorySection[path=..., root=...]`, not null. That's why `ConfigReader.wrongStructure` exists, it produces a clean "found a section/list" issue message instead of quoting that garbage; it is message quality, not correctness (the parse would fail and report either way). `messageStyle` is read via plain `getString` and is safe for the same reason.
- **`Inventory#addItem` declares `throws IllegalArgumentException`** in the API contract (current impl throws for null items, which `DropPickupManager` filters). The try/catch there sits on a declared API boundary and is the last-resort "drop instead of lose" fallback, don't "simplify" it away.
- **`UpdateChecker`'s volatile write order is the publication mechanism.** `parseLatestVersion`/`failCheck` write the payload fields (`latest`, `latestVersion`, `updateAvailable`/`checkFailed`) *before* `checkCompleted`; readers gate on `checkCompleted` first, so the JMM's volatile piggyback guarantees they see the payload. Don't reorder those write, and don't add a lock around the read side.
- **The drop tables apply to every tool; only fortune matters.** `matureDrops` always samples `VanillaCropDrops` with the tool's fortune level from `getEnchantmentLevel(Enchantment.FORTUNE)`. This is vanilla-exact because the staged crop loot tables consult fortune (`apply_bonus`) and nothing else: vanilla itself ignores silk touch, efficiency, and every other enchantment for these drops. The original gate that fell back for any non-fortune enchantment was removed after the 5,933-crop capture showed real (Efficiency-hoe) players never once hit the tables. Fortune above III is fine, the binomial/uniform bonus math is generic in the level; the null-table fallback to `block.getDrops` stays as the fail-safe.
- The update check uses a browser User-Agent against `api.github.com` (rate-limit workaround), leave the header alone.

## Settled decisions (don't re-litigate)

Reviewed and deliberately accepted across audit rounds, each was re-examined and kept:

- **No upper clamp on `maxReplantsPerTick`/`maxReplantsQueued`**, only the ≥ 256 minimums are enforced; going huge is the admin's choice. Don't add a ceiling.
- **Reload drains the old queue synchronously on the main thread**, bounded by queue capacity; don't make it async (blocks would be touched off-thread).
- **CI artifact (zip) name uses `github.run_number`; the jar's `+build.N` uses the git commit count**, the two numbers can drift; the jar name inside the zip is the authoritative one. Don't "sync" them.
- **`TextUtil.prettyName` uses default-locale `Character.toUpperCase`**, every current crop name is ASCII; don't add locale plumbing.
- **`UpdateChecker`'s static `HttpClient` is never closed**, harmless because the server exits via `System.exit`; don't add shutdown plumbing.
- **Queue-full stays a silent drop with a throttled warning** (no throw, no unbounded growth), and `growPool`'s `IllegalStateException` is a deliberate invariant trap, not reachable through `enqueue`.
- **Mature crop drops come from hardcoded transcriptions of the vanilla loot tables** (`VanillaCropDrops` + `loot_tables/`), not from calling `block.getDrops()` at harvest time; tables apply to every tool (vanilla's crop tables read fortune only) with `getDrops` kept as the fail-safe. Maintainer-approved performance amendment to the vanilla-faithful contract; don't re-litigate it back to getDrops-only, and don't reintroduce an enchantment-map gate (it silently disabled the tables for every really-enchanted tool).

## RTK

RTK (`rtk`) is installed and available on PATH. Use RTK commands whenever an equivalent exists to reduce unnecessary CLI output and context usage.

### Rules

- Prefer `rtk` over the normal command when RTK provides an equivalent.
- Use the normal command when RTK does not provide an appropriate equivalent.
- Do not use RTK if the full/raw output is required for the task.
- Do not run both RTK and the normal command just to compare their output.
- RTK only filters/condenses output; it does not change the underlying command's intended behavior.
- If RTK hides information needed to continue, use `rtk recall` when applicable or run the normal command.

- `gh ...` → `rtk gh ...`
- `curl ...` → `rtk curl ...`
- `wget ...` → `rtk wget ...`

Maven has no RTK equivalent, run `mvn` normally.

### Useful specialized commands

- Use `rtk test` when only test failures/results are needed.
- Use `rtk err` when only errors and warnings are relevant.
- Use `rtk diff` for a compact diff when the full diff is unnecessary.
- Use `rtk json` when inspecting JSON output.
- Use `rtk summary` or `rtk smart` when a concise command summary is useful.

Do not blindly replace every command with RTK; if RTK's filtering could hide information needed to continue, run the normal command.

### Shell tools on this Windows machine

- **ripgrep (`rg`)**, real `.exe` on PATH (BurntSushi via WinGet). The default content-search tool: `rg -n "pattern" path`. `rtk rg` works; `rtk grep` does not, it spawns a `grep` binary that does not exist on Windows, so run `rg` directly instead.
- **uutils/coreutils**, Unix basics as real `.exe` shims on PATH (WinGet): `head`, `tail`, `wc`, `sort`, `tr`, `cut`, `seq`, `od`, `basename`, `dirname`, `realpath`, `touch`, `tee`, and the rest of the coreutils set. Nuance: inside Git Bash sessions the GNU coreutils 8.32 in `/usr/bin` shadow the shims; the shims win in PowerShell/CMD. Behavior-compatible for the documented basics.
- PowerShell built-ins shadow some of those names inside a PowerShell session (`ls`, `cat`, `sort`, `cp`, `mv`, `rm`, `echo`, `pwd`, `mkdir`, `sleep`, `test`), there they resolve to the PS cmdlets, whose flags differ from GNU (e.g. `cat --version` fails); spawned subprocesses and non-PowerShell contexts see the uutils `.exe`s. If a tool "is not on PATH" in a fresh shell, restart PowerShell or dot-source the profile (`. $PROFILE`).
- `find` on PATH is Windows `find.exe`, not GNU find, use `Get-ChildItem -Recurse -Filter` or `rg --files` for file discovery.
